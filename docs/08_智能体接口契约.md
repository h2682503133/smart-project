# 智能体接口契约

> 用途：智能体侧（agent / context / tool / ingest 四服务）与 Go 主后端之间的**接口契约**，以及会话生命周期、知识库读取边界的定义；代码实现以此为准
> 依据：`智慧农业系统架构设计.md`（框架基线）、`智慧农业接口设计_修改后.md`（Go 已有接口）、`09_给Go侧的接口与SQL需求.md`（需 Go 新增部分）
> 已定：
> - **消息实时落 PostgreSQL（事实源）**：每轮经 Go 接口写 `chat_messages`（复用 Go 已有表，不新增 SQL 表）；会话状态与上下文窗口由 **agent 侧 Redis 管理判断**（**`ctx:{userId}`** 按用户单会话，Redis 为可重建缓存）；
> - **Redis 窗口 LRU 逐出直接销毁、不写回**：队列（`queue:session.activity`）用于**判定逐出哪个用户**，判定后直接删除缓存（PostgreSQL 已是事实源）；
> - 文档可用性由 Go 判断并保证（智能体只读、无写知识库权限）；**向量库（Milvus）归智能体侧，独立部署、智能体直连，Go 不碰**；
> - 摘要**不落 SQL**：生成后向量写入独立 Milvus 记忆 collection，不与知识一起存储；
> - 已有接口（Go 已实现）**直接复用**，本文件标注引用；**需 Go 新增的只有 2 个**（消息落库、文档清单）；文档通知走 **HTTP**（Go → agent）。
> 状态：**契约定稿，待 Go 侧按此实现/预留**

## 一、会话生命周期与结束判定

### 1.1 状态机

```
active ──(LLM 判定问题已解决，追加询问)──▶ waiting_close
active ──(用户主动点"结束会话"按钮)──────▶ closed
waiting_close ──(用户回复含结束意图)─────▶ closed
waiting_close ──(5 分钟无回复超时)───────▶ closed
waiting_close ──(用户提出新问题)─────────▶ active（回到对话）
```

| 状态 | 含义 |
|---|---|
| `active` | 对话中 |
| `waiting_close` | 智能体已回答并询问"还有其他问题吗"，等待用户回复 |
| `closed` | 已结束（触发摘要生成） |

### 1.2 结束判定（三层，顺序执行）

1. **显式按钮**：用户点击"结束会话"（前端调 agent 侧接口，见 3.2）→ 直接 closed；
2. **意图判定（规则优先，省一轮模型调用）**：智能体询问"还有其他问题吗"后，用户下一条回复**先走规则判断**：
   - 规则命中（正则匹配："没有/不用了/谢谢/没了/就这些/end/no/thanks" 等）→ 直接 closed，**不调 LLM**；
   - 规则未命中 → 走 **LLM 意图分类**（结束 / 新问题 / 继续追问）：
     - 结束意图 → closed；
     - 新问题 → 回到 active，正常进入问答流程；
3. **询问后超时**：`waiting_close` 状态且 `last_message_at` 距今 **> 5 分钟**（可配置）→ closed。

### 1.3 无全局超时

用户任意时刻离开、几天后回来继续问，会话保持 `active`，**不自动结束**（不跑常驻定时扫描）。

### 1.4 超时判定归属

agent-service **惰性检查**：有请求进来时顺手扫描该用户的 `waiting_close` 会话，超阈值则置 closed → 入队摘要。不做后台轮询。

### 1.5 摘要触发

会话 closed 后 → Redis Stream 入队（`queue:session.summary`）→ ingest 消费生成摘要（**≥ 2 条消息才生成**，单条不摘要）→ **摘要向量写入独立 Milvus 记忆 collection**（metadata 含 `session_id / model_version / generated_at / plot_id`），**不落 SQL**；摘要源 = agent 侧 Redis 短期窗口，未命中时从 Go 已有 `GET /api/v1/agent/sessions/{sessionId}/messages` 拉取。

### 1.6 会话状态存储（**不落 SQL，agent 侧 Redis 管理**）

- 会话状态：`agent:session:{sessionId}` = `{user_id, status, last_message_at, plot_id?}`（Redis，惰性检查更新）；
- 短期窗口：**`ctx:{userId}`**（按用户，**不按 session 隔离**——用户同一时间只有一个活跃会话，灌溉聊完归档后才聊植保），最近 N 轮对话（D2 LRU 管理，agent 写回）；
- **聊天记录事实源 = Go 已有表**（`chat_sessions / chat_messages`）：消息**每轮实时落 PostgreSQL**（经 3.3 写接口，JWT），智能体不直连 PostgreSQL、不新增 SQL 表；Redis 窗口为可重建缓存（复用已有 GET 回填）；
- 显式关闭按钮：前端 → agent 侧接口（agent 更新 Redis 状态，不调 Go）。

### 1.7 消息存储与 Redis 窗口（已定：**实时落 PostgreSQL + 逐出直接销毁**）

```
消息：每轮问答【实时写 PostgreSQL】（经 Go 接口落 chat_messages，事实源）
Redis 窗口：ctx:{userId}（最近 N 轮，热缓存，可从 PostgreSQL 重建）+ ctx:active（ZSET，score=最后交互）
容量：最大活跃用户数（可配置，如 1000）
LRU 判定走队列：agent 每轮入队 queue:session.activity {user_id, ts}
  → ingest 消费更新 ctx:active → ZCARD > 上限 → 判定最久未回 K 个用户
逐出动作：DEL ctx:{userId} + ZREM ctx:active，【直接销毁，不写回】
  （PostgreSQL 已有完整记录，Redis 只是缓存，丢了可从 PostgreSQL 重建——02 修订版"Redis 为可重建缓存"原则）
```

- **消息实时落 PostgreSQL**（每轮经 Go 接口写 `chat_messages`，见 3.3），Redis 窗口仅作热缓存；
- **队列用途 = LRU 逐出的用户判定**：判定逻辑由 ingest 消费 `queue:session.activity` 异步完成，请求路径只入队；
- **逐出直接销毁**：判定出的用户窗口缓存直接删除，**无需写回 SQL、无需批量写接口**（PostgreSQL 已是事实源）。

## 二、知识库：职责分工与向量库归属

### 2.1 文档业务状态归 Go，可用性由 Go 判断并保证（已定）

- **智能体不写文档业务状态**：不做文档上传/审核/发布/下线（这些是 Go 侧知识库管理面），智能体**没有写知识库权限**；
- **所有读取到的文档都是可用的**：可用性（审核、版本、状态）由 Go 侧管理并保证——智能体通过检索/查询拿到的文档即视为可用，**不在智能体侧做任何状态过滤**。

### 2.2 向量库（Milvus）归智能体侧（已定，需实现）

- **向量库只有 agent 使用，不归 Go 管**：Milvus **独立部署**，向量化加工（解析/切片/embedding/写入）与检索全部由智能体侧实现，智能体直连 Milvus（Go 不碰、不直连数据库约束不适用于向量库）；
- 加工由 **ingest-service** 负责：收到通知（见 3.4）→ 从 Go 拉取**可用文档清单**（见 3.3，Go 保证均为可用）→ 与 Milvus 已有向量对比（`doc_id + version`）→ 缺失或版本变更的文档执行解析/切片/embedding → 写入 Milvus 知识 collection；
- **触发方式（已定）**：**Go 在文档上传/变更时主动通知**——Go 调 agent 侧通知接口（3.4，内部密钥）→ agent 入队 `queue:doc.process` → ingest 消费拉取加工；**非定时轮询、无向量就绪回写**（Go 不关心向量何时就绪，只负责业务状态）；
- **collection 由 agent 侧建**：知识 collection schema（doc_id / version / category / chunk_text / embedding）初始化归 ingest-service（幂等，存在即跳过）；检索时**无需**再带状态过滤（Milvus 里只有可用文档）。

### 2.3 摘要存储隔离（已定）

- **上下文摘要不与知识一起存储**：摘要向量存**独立 Milvus 记忆 collection**（`source_type=memory`，按 user_id 强隔离，metadata 含 model_version / generated_at / session_id），与知识 collection 物理/逻辑隔离、权限模型不同（D4 定案）；**不落 SQL**（不新增 chat_summary 表）。

## 三、接口契约

统一约定：Go 主后端前缀 `/api/v1`，响应沿用 Go 文档 `{code, message, data}` 格式，时间 ISO 8601；带 JWT（用户数据范围）；`trace_id` 贯穿。

### 3.1 复用 Go 已有接口（智能体只读，带 JWT）

| 智能体能力 | Go 已有接口（引用 `智慧农业接口设计.md`） | 说明 |
|---|---|---|
| get_user_plots（用户田块列表） | `GET /api/v1/plots` | 按当前用户权限返回地块列表 |
| get_latest_telemetry（地块最新遥测） | `GET /api/v1/plots/{plotId}/telemetry/latest` | 已有 |
| get_telemetry_history（历史趋势） | `GET /api/v1/telemetry/history` | 已有（plotId/metric/range/interval） |
| get_farm_overview（总览） | `GET /api/v1/dashboard/overview` | 已有；具体组织由 Go 侧定 |
| get_active_alerts（告警） | `GET /api/v1/alerts`、`GET /api/v1/alerts/logs` | 已有；告警判断归 Go，智能体只读 |
| get_alert_rules（阈值规则） | `GET /api/v1/plots/{plotId}/thresholds` | 已有（含 operator：LT/GT） |
| get_device_status（设备状态） | `GET /api/v1/devices`、`GET /api/v1/devices/{deviceId}/status` | 已有 |
| 用户标签（System 段用） | `GET /api/v1/users/me` | ⚠️ 已有但**缺 `interaction_style` / `knowledge_reliance`**——需 Go 补返回字段（见 09 §2.1） |
| 短期窗口回填 | `GET /api/v1/agent/sessions/{sessionId}/messages` | 已有（接口文档 §8.2）；Redis 未命中时回填（D2） |

### 3.2 智能体侧自管与暴露（不涉及 Go 接口）

| 能力 | 实现 | 说明 |
|---|---|---|
| 问答入口 | `POST /agent/chat`（agent-service，SSE 流式） | 入参 `{session_id?, plot_id?, question}`；JWT；会话不存在自动创建 |
| 会话状态机 | agent 侧 Redis（`agent:session:{sessionId}`） | active / waiting_close / closed，不落 SQL |
| 短期窗口 | agent 侧 Redis（**`ctx:{userId}`**，按用户单会话） | D2 LRU 管理：每轮入队 `queue:session.activity`，判定走 ingest 消费者；逐出直接销毁缓存（1.7） |
| 显式结束 | `POST /agent/chat/sessions/{id}/close` | 前端按钮 → agent 更新 Redis 状态 → 入队摘要 |

**SSE 事件类型（`POST /agent/chat` 返回流）**：

| 事件 | data | 说明 |
|---|---|---|
| `started` | `{type: started}` | **占位事件：立即发出响应头**，客户端无需等首 token（TTFT 感知） |
| `answer` | `{type, delta}` | 回答增量（逐 delta 流式；**含中间回复**与**最终回复**） |
| `tool_call` | `{type, tool_calls:[{name, arguments}]}` | **Agent 正在调用工具**（结果发回 LLM 继续，直到不再调用） |
| `done` | `{type, sessionId, canClose, closed, sources}` | 收尾：canClose=是否询问"还有其他问题吗"；sources=引用（docId/title/version/score） |
| `error` | `{type, message}` | 异常（会话超时结束等） |

> 问答采用 **Agent 循环**（**零 Go 接口变更**）：同一 messages 对话中，LLM 流式生成 → 若返回 tool_calls 则执行并把结果以 `role=tool` 回填 → 继续生成，**直到 LLM 不再调用工具**。**最终回复以 `【最终回复】` 文本前缀标注**（代码判定：该轮无工具调用=最终回答，非 LLM 完成），前端据此区分中间回复（可能多条）与最终回复。用户一条提问可能顺序收到多条回复。

### 3.3 需 Go 新增（2 个）

| 方法/路径 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `POST /agent/sessions/{id}/messages` | body: `{role, content, citations?, plot_id?, model_version}` | `{message_id, created_at}` | **每轮消息实时落库**（事实源写 `chat_messages`，JWT）；同时更新 `last_message_at` |
| `GET /api/v1/knowledge/docs` | query: category? | `[{id, title, category, version, file_url, updated_at}]` | 只返回**可用**文档（Go 保证可用性）；ingest 加工源、检索元数据对照 |

### 3.4 Go → 智能体侧（1 个，HTTP 通知接口，agent-service 提供）

| 方法/路径 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `POST /internal/knowledge/notify` | body: `{doc_id, event: uploaded/updated/archived, version}` | `{ok: true}` | **Go 在文档上传/变更时主动通知**；agent 入队 `queue:doc.process` → ingest 消费拉取加工；**内部服务密钥**校验，立即返回不阻塞 Go |

> 接口总数：**复用 Go 已有 9 个 + Go 新增 2 个 + agent 提供 1 个**；文档通知走 HTTP；**队列仅用于 LRU 逐出判定（`queue:session.activity`）与加工/摘要（`queue:doc.process` / `queue:session.summary`）**；消息实时落 PostgreSQL（3.3 写接口），Redis 窗口逐出直接销毁；向量库（Milvus）归智能体侧。

## 四、端口与调用约定

| 服务 | 端口 | 说明 |
|---|---|---|
| Go 主后端 | `8080` | REST，前缀 `/api/v1`（智能体侧同域调用） |
| agent-service | `8000` | REST + SSE（前端入口）+ `/internal/*` 通知路由（仅 HTTP fallback 时用） |
| context-service | `8001` | REST（agent 内部调用） |
| tool-service | `8002` | REST（agent 内部调用） |
| ingest-service | `8003` | 无对外 HTTP，消费 Redis Stream（`queue:doc.process` / `queue:session.summary` / `queue:session.activity`）+ 写 Milvus |

- 服务间用 **compose 内服务名 + 端口**（内网 DNS），不走公网；
- **认证分层**：JWT（用户数据范围）只在 agent → tool/context → Go 链路透传；Go → agent（3.4 通知）用**内部服务密钥**（共享密钥头，非 JWT）；
- `trace_id` 贯穿：前端 → agent → tool/context → Go → LLM → Milvus；
- **LLM/Embedding 定案（实现确认）**：对话模型 DeepSeek（`deepseek-v4-flash`，OpenAI 兼容流式）；向量化火山方舟 `doubao-embedding-vision-250615`（`POST /api/v3/embeddings/multimodal`，结构化 input + `dimensions=1024`，逐条调用）；embedding 双模式（multimodal/standard）由 config `embedding.mode` 切换；
- **队列消费可靠性（实现确认）**：ingest 消费"成功才 ACK"；处理失败**重投**（retry 计数，超 3 次丢弃），消息不丢失。

## 五、待 Go 侧确认/实现项

1. **复用接口（9 个）**：`智慧农业接口设计.md` 已定义，直接复用；`GET /users/me` 需补 `interaction_style` / `knowledge_reliance` 返回字段（见 09 §1.1）；

4. **Redis Stream 队列约定**：
   - `queue:session.activity`：交互事件（**LRU 逐出用户判定**用，agent 入队 → ingest 消费判定 → 逐出直接销毁缓存）；

   - `queue:session.summary`：会话摘要；

5. 会话/消息：**不新增 SQL 表**，复用 Go 已有 `chat_sessions / chat_messages`；消息**实时落 PostgreSQL**（经 3.3 写接口），Redis 窗口为可重建缓存，**逐出直接销毁、不写回**；
6. `GET /agent/sessions/{sessionId}/messages`（复用）用于 Redis 未命中回填窗口。
